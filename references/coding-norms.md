# Student Coding Norms & Authentic Human Imperfection Rules

Follow these rules strictly to ensure all generated code matches the natural coding style of an undergraduate student.

## 1. Strict Minimal Scope & No Assumptions (CRITICAL)
- **NEVER** do anything more than what is explicitly required in the lab task or what the user specifies.
- **NEVER assume anything about the lab task.** If at any point you are confused or requirements are ambiguous, **consult the user in a clear, basic manner** before proceeding.
- **NEVER** invent extra features, helper methods, classes, configurations, or input validation that the manual did not ask for.
- Solve ONLY the exact problem stated, nothing more, nothing less.

## 2. Authentic Student Formatting & Imperfections
- Do **NOT** write perfectly formatted, PEP-8 / Google-style polished code.
- **Randomize whitespaces and formatting:**
  - Inconsistent spacing around operators and slices: `message[i: i+214]`, `a = b+ 1`, `arr[ i ]`, `val = a *b`.
  - Inconsistent empty lines: Leave an accidental blank line between function calls or before returns.
  - Simple procedural structure: Use standard `open()` and `close()` instead of `with open(...) as f:`.
  - Simple returns: Include a casual `return` statement at the end of void or None functions.
  - Quick student comments: Use simple tags like `###MAIN###` or `#Encryption` or simple lowercase fragments (`// loop through arr`).
- The code must look like it was written during a 2-hour lab session by a real student, NOT generated by an enterprise linter.

## 3. Console & Terminal Output Rules
- In the terminal or script print statements, **NEVER** show headings using `----heading----` or `====heading====`.
- Always use the simple format: `heading: ` (e.g., `Task 1: `, `Result: `, `Output: `).
- Simple, unpretentious prompts: `Enter number: `, `Successfully encrypted`.

## 4. Comment Hygiene
- **NEVER** write Doxygen comments (`/** @brief ... */`), Python docstrings (`"""Calculates the..."""`), or multi-line decorative banners (`// ==========================`).
- **NEVER** write full-sentence comments ending with periods (`// Initialize the variable to zero.`).
- Write at most 1–2 brief comments per 30 lines of code, only for non-obvious logic (`// read in chunks`, `// decrypt block`).

## 5. Naming & Structure
- Use short, natural student variable names: `n`, `m`, `i`, `j`, `key`, `msg`, `arr`, `in_doc`, `out_doc`, `temp`, `ans`, `res`, `curr`, `prev`.
- Avoid enterprise names (`calculateRsaCiphertextBlock` -> `encrypt`).
- Keep code flat: define functions simply and invoke them at the bottom in a `###MAIN###` or basic execution block.

## 6. Language-Specific Guidelines
- **Python:**
  - **NEVER** use type annotations (`def solve(arr: list[int]) -> int:` is forbidden; use `def solve(arr):`).
  - Do **NOT** use `if __name__ == "__main__":` on simple single-file lab scripts—just write the main logic at the bottom.
  - Avoid `argparse` or `logging`; use straightforward `input()` and `print()`.
- **C++:**
  - Always include `using namespace std;` at the top. Never prefix everything with `std::`.
  - Include only standard taught headers (`<iostream>`, `<vector>`, `<string>`, `<cmath>`).
  - Do not use `try/catch`, `constexpr`, `noexcept`, `std::optional`, or complex lambda expressions unless specifically requested.
